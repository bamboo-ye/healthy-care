# 伴AI·健康伙伴前端原型设计

本页主要记录前期本地原型。最终信息架构和后续开发方案见[最终需求设计与开发计划](final-requirements-and-plan.md)；新版科研端采用数据概览、数据分析、队列管理、记录查询、数据管理、分析任务和文献库七个操作页面，报告式研究论证与参赛材料不进入产品主页面。

用户端以亲切的自然语言对话为主。用户直接描述身体感受、用药和变化，助手在对话中追问、整理和确认，不要求用户选择病种或症状类别。产品面向所有符合自主处理条件的日常小病，湿疹只是案例之一。科研端是独立入口。

当前实现的是本地交互原型，未接入真实AI、医学判断或后端。个人端初始没有个人记录，但每日健康展示通用日常关照，不预置症状、评分、用药或病程；科研端使用独立的合成研究数据。

## 一 视觉与布局

保留参考项目的侧栏加工作区、圆角字体、柔和卡片、助手消息在左和用户消息在右的布局。用户端只展示健康功能，不显示其他业务模块。

品牌名保持伴AI·健康伙伴。新绘制的绿色角色logo延续云朵发型、耳机、圆润表情和柔和光影。绿色房间背景保留中心留白，浅色侧栏、聊天面板与背景柔和叠加。

| 元素 | 设计约定 |
| --- | --- |
| 桌面壳层 | 268px侧栏加主工作区，小屏按断点收窄 |
| 用户端导航 | 每日健康、健康对话、我的病程、我的用药、历史线索；我的与授权位于个人入口 |
| 默认工作区 | 每日健康，保留对话输入；不展示病种选择器、预置病程或默认用药 |
| 对话气泡 | 助手浅色气泡，用户浅绿气泡，消息可附图片和确认卡片 |
| 输入区 | 多行文字、图片按钮、待发送图片预览、发送按钮 |
| 结构化信息 | 在消息内展示已整理字段与来源，供用户查看或用自然语言更正 |
| 品牌素材 | health-mascot-green.png用于侧栏、助手头像和欢迎状态 |
| 背景素材 | health-background-green.png用于用户端背景 |

核心token为 `--ink: #553e3a`、`--muted: #7c6864`、`--module-accent: #287453`、`--module-soft: #e3f2e7`、`--health-bg: #e4f1e6`。绿色是视觉主题，不代表医学意义上的正常。

### 用户端模块布局

用户端使用独立的 `prototype/user-layout.css`，只由个人端入口加载，避免布局规则影响科研端。工作区最大宽度为1220px，常规卡片间距20px、内边距24px、圆角24px。各卡片统一图标标题、来源或状态标签、正文、底部操作的层级。

桌面每日健康将问候与图文输入并排收纳到一个紧凑卡片，减少顶部占高。无进行中不适时，日常、康复与环境建议统一放入一个“今日关照”模块，内容结合恢复记录、个人背景、城市和天气等因素组织；天气不是单独模块。关照下方再以两列展示历史健康数据观察和历史记录小结，避免重复建议和卡片拉长。有进行中不适时，当前分析与评分趋势、护理建议与下一步观察分别成对对齐。

病程卡片在桌面并排展示趋势和记录时间线，手机按顺序上下排列。用药采用卡片列表，历史线索采用主内容与说明卡，个人授权采用选择状态与解释卡。查询页保持适合阅读的宽度，不用大面积拉长正文。

1150px以下问候和输入改为上下排列；1000px以下主要信息卡片切为单列。手机使用16px间距与20px卡片内边距，标题、按钮和标签按内容换行。图文消息使用固定尺寸的完整图片缩略图，预留加载空间，点击仍可查看大图。

## 二 每日健康与无当前不适状态

每日健康保留简洁、有依据的分析、建议和观察重点，不复述整段聊天。用户可以随时通过健康对话完成所有业务操作。

| 状态 | 每日健康显示 |
| --- | --- |
| 首次使用、没有历史 | 角色与问候、文字和图片输入、通用日常关照、个人环境背景补充入口 |
| 有正在跟进的不适 | 用户描述与已知持续情况、实际自评分、来源清晰的护理资料、实际观察点、用药待核对项和下一步观察重点 |
| 不适已结束、有历史 | 统一的今日关照，结合康复、个人背景和环境因素生成建议；另附已归档记录小结与历史数据观察 |
| 有优先求助信息 | 当前行动优先于普通护理与关怀内容 |

用户表示恢复或结束本次跟进后，将事件归档并取消当前事件指向。首页可以展示已结束病程，但明确标为“已结束 · 非当前问题”，不恢复随访、不默认续用旧药，不将用户标记结束解释为医学确认治愈。

历史观察只从实际记录计算，例如已结束事件数、重复描述的主题、已有评分和自报用药完整性；数据不足时说明限制，不制造疾病模式、诊断或患病概率。正式版可由历史检索与知识匹配生成更深入、带日期和来源的观察，并保留建议版本。

季节与天气关照优先使用用户主动提供的城市、已知过敏、容易干燥等背景。当前原型没有天气服务，明确标注天气待接入，仅展示条件性环境建议。正式版须显示气象来源、地点、更新时间和适用条件；过期或缺失时退回通用建议。城市可通过“我在上海”等对话补充，不自动定位。

用户说“我很好”“没有不舒服”，或仅补充日常背景时，不自动创建症状事件。图片单独发送时先询问上下文。历史回顾不会重新激活旧病程。

## 三 对话状态与主要流程

| 状态 | 界面与行为 |
| --- | --- |
| 首次进入 | 每日健康、欢迎语、日常关照、文字与图片输入，无预置疾病 |
| 描述不适 | 保留原话，助手逐步追问开始时间、程度、影响和相关变化 |
| 整理信息 | 消息内呈现用户自述字段，区分未知、未记录与否定；可直接说“不是手臂，是腿部”来更正 |
| 自主处理信息 | 根据适用范围、危险信号和知识来源组织护理与OTC信息；原型不生成真实个体用药方案 |
| 记录用药 | 用户描述具体产品与实际使用，药盒图片可一起发送，缺失字段继续追问 |
| 每日随访 | 用户说“今天好些了，3分”“今天没用药”等，整理成当天记录，重复补充更新版本 |
| 提醒 | 用户说“每天晚上8点半提醒我记录”，保存站内计划；可用对话暂停 |
| 结束跟进 | 用户表示恢复或结束，归档当前事件，回到无进行中不适状态 |
| 查看历史 | 用户主动请求回顾，展示只读病程、实际记录趋势和来源 |
| 研究与隐私 | 对话解释用途，用户明确同意或撤回，图片研究独立选择 |

症状主题用于内部知识检索和随访字段组织，不要求用户选择。所有场景共用对话与事件模型，通过知识资料和适用性判断决定能提供什么信息，而不是用静态病种菜单限定范围。

## 四 对话功能映射

| 功能 | 用户可以这样说 | 预期行为 |
| --- | --- | --- |
| 开始描述 | “这两天喉咙有点不舒服” | 建立基于自述的信息记录并继续追问，不直接确诊 |
| 图片输入 | “这是皮肤的照片”“这是药盒” | 图片与消息关联，结合文字上下文继续问询 |
| 用药记录 | “我今天用了某个产品，包装上写……” | 保存自述，核对名称、成分、规格和实际使用 |
| 用药核对 | “这个还能继续吃吗？” | 追问具体产品、时间与变化，对照对应说明，不按天数一刀切 |
| 每日变化 | “今天大概3分，睡得好一点了” | 更新当天观察，保留原话与版本，不编造缺失日期 |
| 历史回顾 | “帮我看看之前的病程” | 回顾用户已记录的内容，不自动变成当前疾病 |
| 早期线索 | “这些变化会不会有什么早期表现？” | 检索历史与经审阅知识，展示依据与缺失信息；原型只演示流程 |
| 设置提醒 | “每天20:30提醒我记录” | 设置站内计划；真实推送需后端调度 |
| 研究授权 | “我想了解研究授权” | 解释用途并给出明确的允许、暂不参与与撤回操作 |
| 导出 | “导出我的记录” | 生成本地个人JSON摘要，图片文件不直接嵌入 |
| 清除 | “清除本次记录” | 在对话内展示具体影响，用户明确确认后清除 |
| 结束事件 | “我已经好了，结束这次记录” | 归档，首页显示康复与日常关照并询问新需求 |

用药、授权、归档等动作可以通过对话完成，也可以点消息里的操作按钮；操作按钮使用明确的自然语言。字段更正、复杂否定、多个并行事件与完整知识判断属于真实模型和后端需要完成的能力，本地原型不能据此宣称已经实现通用自然语言理解。

## 五 图片输入

文字和图片可一起发送，也可仅发送图片。每条消息最多4张，每张不超过8MB，支持PNG、JPEG和WebP。

选择后先在输入框上方预览，可逐张移除；添加或移除图片保留文字草稿。发送后图片附在用户消息中，点击可放大。当前使用浏览器本地对象URL，不上传图片，也不声称完成真实图像理解。

正式版本应通过受控附件接口上传，检查内容和大小、移除EXIF、按用途授权、加密存储，并将附件ID和消息关联。图片分析要结合文字、时间和症状，不能用图片替代临床诊断；质量不足时解释原因并请求补充，不默认输出病名。

## 六 只读查询视图

对话是所有业务操作的主入口，保留每日健康摘要与个人查询视图，帮助用户回顾已确认的信息。

| 用户视图 | 内容与空状态 |
| --- | --- |
| 每日健康 | 当前分析与建议；无当前不适时展示康复、历史观察和季节关照 |
| 我的病程 | 用户真实描述、每日记录、只基于已有评分的趋势；没有记录时邀请对话，不显示虚构历史 |
| 我的用药 | 用户自述的实际使用信息与待核对字段；无记录时邀请说明或发药盒照片 |
| 历史线索 | 有依据才能匹配；无历史时说明信息不足，不展示疾病概率或“没有大病”的保证 |
| 我的与授权 | 当前研究、影像、提醒和数据状态；操作通过对话完成 |

科研端包括研究总览、分析工作台、研究设计、队列与质量、记录溯源、数据底座、SciencePal运行和研究依据八个视图，不在用户端显示角色切换。科研端中的病程教学样例必须标注为合成，不能冒充个人端历史。

## 七 独立前端结构

| 文件 | 职责 |
| --- | --- |
| prototype/index.html | 用户端独立入口 |
| prototype/app.js | 对话、图片、当前事件与归档、用药、授权和查询视图 |
| prototype/research/index.html | 科研端独立入口 |
| prototype/research/app.js | 科研页面、筛选、溯源、运行、结果导入与导出 |
| prototype/research/engine.js | 固定合成样例、字段配对、用药候选、缺失与时间规则 |
| prototype/research/research.css | 科研端的专业绿色布局与响应式 |
| prototype/research/run_analysis.py | 可下载、可在SciencePal执行的无依赖参考分析 |
| prototype/styles.css | 两端基础视觉token与共享样式 |
| prototype/user-layout.css | 仅用户端的卡片、模块、对话与响应式布局 |
| prototype/shared.js | 基础图标与转义工具 |
| prototype/assets | 绿色角色、背景与科研图标 |

本地窗口联动只用研究授权开关控制一个合成样例的入组，不向科研端发送用户对话、症状或图片。这不是认证或真实研究接口。正式版本必须使用后端权限、独立研究视图、用途授权和审计。

后端的对话接口应返回助手消息、待确认的结构化提取、明确的状态变更、证据与失败原因；附件作为消息的独立资源。以消息ID和事件版本保证幂等，同一天随访更新版本，不能因重试增加患者日。

## 八 可访问性与验证边界

输入框有可读label，支持Enter发送、Shift加Enter换行和输入法组合输入。对话使用log区域，图片有替代文本，按钮保留键盘焦点，弹窗支持Escape，手机布局不发生页面级横向溢出。

没有评分时显示记录不足；只有一天时只显示一个观测点，不补造曲线。所有医学推断、药品知识与真实通知都需后端实现。本地规则只用于验证对话与页面状态，不能作为临床效能或通用Agent能力的证据。

素材由内置图像生成工具绘制，路径与提示词见 `image-assets.md`。

科研工作台的研究依据、计算定义、报告契约和验证协议详见 `research-design.md`。它不包含真实患者诊疗或医生确认流转。
