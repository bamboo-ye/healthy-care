# 伴AI·健康伙伴项目需求

本页保留前期需求与原型范围。2026年10月19日汇总后的功能、科研端产品组织、技术架构与排期以[最终需求设计与开发计划](final-requirements-and-plan.md)为准；本页对既有原型的描述不代表新版工程已经开发。

更新日期：2026年10月18日。项目面向所有适合自主处理、可依非处方药说明自主用药的日常小病；湿疹与皮肤问题只是示例之一。核心是让一次咨询转为连续健康记录，并在独立研究授权下形成可追溯、可复现的数据分析。

产品定位：**以亲切自然语言对话为主的独立日常健康助手，为日常小病提供症状梳理、自我护理和非处方药信息、用药记录、随访提醒，并从个人历史记录中匹配值得排查的疾病相关线索。** 医生确认、真实在线问诊和购药不进入本届主流程。

本文中的“应实现”是竞赛作品的目标范围；当前交付的前端是合成数据原型，不代表这些后端、医学知识和平台能力已经实现。

## 二 用户价值与科研问题

### 用户问题

用户常在轻症出现时自行查资料或购药，但缺少统一的病程、实际用药和变化记录。再次不舒服时，历史信息分散在照片、聊天和记忆里，容易重复用药、忽略产品说明或无法判断何时需要进一步求助。

健康伙伴应回答四个具体问题：现在有哪些信息需要补充；当前是否仍适合自主处理；已选用的具体药品应核对哪些说明；与前几天相比有什么变化、下一步应观察什么。

### 主研究问题

**相较于单次自由对话记录，结构化的连续随访能否更完整地还原院外轻症过程，并识别需要核对的自主用药偏离？**

目标产物是可追溯的数据集、可解释的规则输出、明确的数据质量报告和方法比较，不直接宣称减少药物滥用或改善临床结局。

研究中的“疑似偏离”指向已核对的具体说明书或用户已有用药计划，例如记录频率与所选产品说明不一致、重复成分、无法识别成分、到达原计划复核节点。它不等于已经证实滥用，更不能仅凭用药天数下结论。

### 历史症状与知识库匹配

保留用户提出的“防大病”能力，准确表述为：**把个人历史症状、持续情况、体重等自报数据和用药记录，与知识库中的疾病相关表现匹配，识别值得进一步排查的症状组合。**

其输出必须包含历史证据、匹配来源、还缺的信息与可执行建议。例如，在独立演示样例中，历史记录同时出现持续口渴、尿频、非主动体重下降，可以匹配糖尿病相关症状资料并建议就医检查。NHS列出这些相关症状，并说明诊断需要血液检查；这不意味着系统能判断疾病处于早期，或能凭症状识别糖尿病前期。[NHS症状与诊断](https://www.nhs.uk/conditions/type-2-diabetes/symptoms/)

此能力首版以一个经过专业审阅的有限知识主题做方法演示。由症状匹配推出实际疾病风险、临床敏感度或早诊价值，仍需要独立验证。用户没有出现某项症状，不能被系统解读为排除了疾病。

## 三 范围与优先级

P0代表10月31日前完成闭环所必需；P1代表闭环跑通后增强；P2是本届只展示概念的能力。

| 范围 | P0竞赛必做 | P1增强 | P2概念 |
| --- | --- | --- | --- |
| 轻症范围 | 面向所有符合自主处理条件的小病；通用对话与事件框架、内部随访模板与知识检索，覆盖感冒鼻咽、皮肤、轻度过敏、胃肠、轻微疼痛等代表场景及其他入口 | 扩充知识条目、特殊人群与个性化随访模板 | 超出自主处理条件的诊疗、自动处方 |
| 自主处理 | 明确适用范围、危险信号、护理信息、地区与产品级OTC信息 | 更多经审阅产品知识 | 自动诊断、处方推荐不作为目标 |
| 用药 | 手动确认具体产品、实际使用、重复成分与说明核对 | 药盒OCR、条码识别 | 购药、支付、配送 |
| 连续管理 | 每日随访、病程时间线、提醒任务、异常提示 | 可穿戴数据、跨病程关联 | 不间断医疗监护 |
| 早期线索 | 历史检索、一个有限知识主题匹配、来源与缺失信息展示 | 经审阅的主题扩展与个体基线 | 未验证的全疾病预测 |
| 数据 | 独立研究授权、结构化存储、版本与来源、数据质量、受控导出 | 标准资源映射与更细权限 | 对外开放数据市场 |
| 专业端 | 只读数据概览和队列展示 | 更细粒度分析 | 医生确认、远程诊疗、处方审核 |
| SciencePal | 真实运行数据检查和研究分析；保存可复现结果 | 周期分析任务 | 自动开展人体研究 |

首版不将儿童、孕哺期、免疫功能受损、病情明显严重或信息不足的用户纳入自主用药建议范围；提供记录和合适的求助提示。各类成人轻症都需先检查危险信号。该适用范围是本项目的实现选择，不是赛事额外规定。

### 通用轻症场景与观察模板

轻症不是按病名直接放行。所有场景共用适用性检查、症状与用药记录、知识检索、持续随访和求助升级框架，再按具体症状加载观察字段。下面是首批代表场景，不是产品范围的封闭清单；其他不适同样允许输入，由知识与适用性结果决定能提供哪些自主处理信息。

| 场景 | 记录与随访字段 | 用药信息核对重点 |
| --- | --- | --- |
| 感冒鼻咽不适 | 鼻咽症状、咳嗽、体温记录、持续情况、呼吸与日常活动变化 | 复方产品重复成分、具体产品使用边界、特殊人群 |
| 局部皮肤不适 | 瘙痒或疼痛、部位、范围、渗液、接触因素、可选照片 | 剂型浓度、使用部位、OTC属性、已有计划 |
| 轻度过敏样症状 | 鼻眼症状、可能诱因、睡眠影响、是否出现急性变化 | 成分、嗜睡等说明、重复用药和禁忌 |
| 胃肠不适 | 疼痛与排便、呕吐、进食饮水、症状变化 | 区分症状类型、禁忌、实际使用与说明边界 |
| 轻微疼痛 | 部位、强度、开始及持续情况、活动和睡眠影响 | 重复成分、剂量频次、长期反复使用与适用条件 |
| 其他可自主处理的不适 | 通用主诉、时间、严重度、已有处理、相关变化 | 检索到合适知识并核对具体产品后再输出适用信息 |

评分的含义按场景定义，不能把鼻咽不适分与瘙痒分直接横向比较。研究分析应按主题分层，分别报告相应分母。跨场景可以研究记录完整性、用药字段质量、重复成分候选等共通问题。

资料参考包括[NHS感冒](https://www.nhs.uk/conditions/common-cold/)、[NHS鼻部过敏](https://www.nhs.uk/conditions/allergic-rhinitis/)、[NHS胃肠症状](https://www.nhs.uk/symptoms/diarrhoea-and-vomiting/)和[NHS头痛](https://www.nhs.uk/symptoms/headaches/)。这些资料支持场景设计，不能把英国的药品分类直接作为其他地区的OTC清单。

“自主用药”不代表所有激素、抗生素都可以自行购买使用。知识库必须核对拟服务地区和具体产品的非处方药状态；既有处方药可作为用户实际用药记录，系统不自动开立、续方、加量、停药或换药。

科研端当前实现以四个问题展开：同一病程的5项共同字段覆盖对照、院外用药情境候选、缺失状态的极端敏感性边界、历史症状组合的时序与否定测试。已增加实际本地计算、哈希绑定、Python复现与报告导入校验；全部使用固定合成数据。领域研究依据、公式、实际计算和未完成的临床验证边界见 `research-design.md`。

### 对话优先与无当前不适状态

用户不需要选病种或填写首诊表单，症状、持续情况、实际用药和每日变化从自然语言与图片中获得；模型逐步追问，已提取内容在消息中确认。结构化是内部数据能力，不是让用户承担表单填写。

用户初次进入或没有正在进行的不适时，显示“今天有什么不舒服的地方，或有什么健康问题想了解？”。不预置疾病、评分或用药，也不把已结束的历史病程当作当前问题。明确结束后归档，首页保留问询入口，同时展示康复后的建议、明确标注已结束的历史小结与数据观察、结合个人背景的季节环境关照。历史展示和回顾不会重新激活病程；首次没有历史时提供通用日常关照。

图片与文字可以一起发送。首版交互支持每条最多4张、每张8MB以内的PNG、JPEG或WebP，发送前预览移除、发送后放大。当前前端只本地预览，不上传或进行真实图片识别；真实服务需受控上传、质量评估与图文联合分析。

所有操作应有自然语言入口，包括用药记录与核对、每日随访、提醒、查看病程、知识匹配、授权撤回、导出、清除与归档。研究和影像用途需要明确同意，不能把一般对话中的“好”解释为广泛研究授权。

## 五 三条核心流程

### 自主轻症管理

没有当前事件时询问新需求 → 用户用对话描述并可附图片 → 逐步追问与消息内结构化确认和危险信号检查 → 自我护理与相关OTC信息 → 用户自行确认选择与记录 → 每日随访 → 趋势与使用核对 → 缓解归档并回到无进行中不适的询问状态、继续观察或就医提示。

无需医生确认即可使用。对于超出范围、无法核实的药品或危险信号，系统直接说明为何不适合继续依据本工具自主处理，并给出求助信息。

### 历史记录匹配疾病相关线索

新增症状或定期任务 → 读取允许使用的个人历史 → 时间、单位与否定词核对 → 检索相关知识条目 → 检查组合条件、持续情况与缺失信息 → 生成可解释的线索卡 → 用户补充或更正 → 更新提示与后续观察任务。

当“持续口渴”“尿频”“非主动体重下降”等多个自述同时存在时，可展示糖代谢相关症状资料；原型中的组合匹配仅为演示规则。不能从该规则得出患病概率、疾病阶段或排除诊断。知识资料中的单项症状不能被擅自改写成经验证的组合筛查工具。

### 授权数据研究

用户独立同意 → 生成去标识化研究视图 → 过滤撤回与不可用记录 → 冻结队列和数据快照 → SciencePal真实执行质量检查与分析 → 导入带溯源的报告 → 展示指标、局限与导出包。

研究端不反向访问身份信息；研究授权不是医生分享授权。用户撤回后，后续分析与新导出应排除其记录，派生数据与历史导出的处理边界在授权文本中说明，不能承诺自动收回已经下载的数据。

## 六 业务规则

1. 先判断本工具适用性，再给自我护理与产品信息。发现危险信号时跳过常规长追问。
2. 模型负责提取、追问与解释；重要分流、药品适用范围、授权过滤和单位核对采用可测试的确定性检查。
3. 图片是辅助输入。模糊、光线差、肤色差异和外观相似均可能影响描述，不将图片识别结果直接存为诊断事实。
4. 产品级药品条目包含成分、规格、剂型、途径、地区、OTC状态、适用范围、说明版本。不可把同成分的不同剂型和浓度视作同一产品。
5. 不使用“激素连续7天就停”“抗生素都不应使用”等统一规则。风险与具体药、途径、部位、剂量和持续时间有关；骤停部分激素可能有风险。[NHS激素用药](https://www.nhs.uk/medicines/steroids/)
6. “能不能继续用”必须基于具体产品信息、已有计划与变化，返回对应说明、信息缺口和求助行动；不凭对话即兴生成续方决定。
7. 未填写不等于未使用，症状缺失不等于无症状；一次事件不能合并为多个独立患者。
8. 临床事实、自报事实、AI提取与知识推断分层存储。医生确认状态可在未来加入，但不是本届数据进入流程的门槛。
9. 每个提示有触发依据、来源版本、生成时间和失效条件；同一问题去重提醒，症状加重允许升级。
10. 未经校准不展示诊断概率或“健康分”。早期线索提示可以不成立，且没有提示也不排除疾病。
11. 研究画像只使用独立授权的数据；服务功能不因拒绝研究而受限。医疗记录按用途和权限隔离，不能默认转作无关用途。
12. 用户端和科研端使用独立入口，正式产品必须由服务端分配访问权限；页面分开本身不等于权限隔离。

### 核心实体

## 八 SciencePal的核心工作

SciencePal官方用户指南描述了领域Agent、隔离运行环境、代码执行和持续Workspace等能力，可用于本项目的分析工作流。[SciencePal用户指南](https://sciencepal.ai/help) 当前没有验证其可供本项目调用的具体公开API及配额，因此优先采用“平台实际运行研究任务，前端导入结果文件”的可交付路径。

### 最小真实工作流

1. 准备经过研究授权的去标识化样例；本届演示默认使用明确标注的合成数据。
2. 在SciencePal Workspace放置 `observations.csv`、`medication_use.csv`、`consents.csv`、`knowledge.json`、`cohort.json` 和 `data_dictionary.json`。
3. 在SciencePal中执行版本化分析脚本，先检查授权、单位、缺失、重复和时间关系，再构建患者日表。
4. 计算随访完整率、用药记录缺口、规则候选分布；对比单次记录和连续记录的字段还原表现。
5. 对历史线索样例运行固定知识主题匹配，输出命中证据与缺失信息，不推断真实疾病标签。
6. 输出 `report.json`、`quality.csv`、`cohort_summary.csv`、图表、方法说明和执行记录。
7. 前端导入 `report.json` 后展示平台、run_id、队列、数据来源、输入哈希和脚本版本；保留原始文件供评审下载核对。

若平台允许且有文档，再实现服务端适配器；凭据留在服务端，不把密钥写进前端。不得用“运行中”的动画代替真实平台执行证据。当前科研端提供实际本地参考计算、Python脚本下载与结果导入；本地报告明确标注local-browser或local-python，不把它作为SciencePal执行证据。

`report.json`最小契约包含：`schema_version`、`run_id`、`platform`、`data_origin`、`input_sha256`、`code_version`、`knowledge_version`、`cohort`、`denominators`、`metrics`、`exclusions`、`limitations`、`artifacts`。导入文件本身不证明来自平台，真实提交还需可访问运行链接和日志。

## 九 科研验证与证据边界

院外日常记录可以是待研究的真实世界数据来源，但收集到数据不等于已经得到可靠真实世界证据。FDA对两者作了区分；本项目借用这一方法学区分，不声称符合药品监管证据标准。[FDA定义](https://www.fda.gov/science-research/science-and-research-special-topics/real-world-evidence)

### 本届可完成的验证

| 验证项 | 数据与基准 | 指标和拟验收目标 |
| --- | --- | --- |
| 结构化提取 | 约40条人工编写或经授权去标识化记录；双人独立标注并解决分歧 | 症状、时间、用药字段macro F1；拟目标≥0.90，未测量前不得称已达到 |
| 连续记录价值 | 同一合成病例只给首次记录，对比完整随访；规则与知识固定 | 字段完整率、用药偏离候选召回、误报；按病例分组并按症状主题分层，避免患者日泄漏 |
| 用药规则 | 至少20个边界样例：未知药、重复成分、未记录、剂型差异、原计划变化 | 预期行动与规则一致；危险错误单独报告；不把标签等同真实滥用 |
| 早期线索匹配 | 至少20个阳性、阴性和信息不足样例，含否定词、时间错位、单位错误 | 证据引用准确率、组合条件一致性、信息不足处理；属于方法测试，非临床筛查效能 |
| 分流与来源 | 明确超范围样例和知识失效样例 | 超范围正确回退；没有来源时不产生产品级用药结论 |
| 数据与授权 | 拒绝研究、撤回、影像不同意、重复记录、导出 | 未授权研究记录为0；重复随访不增加患者日；撤回后新查询与导出被排除 |
| 可复现性 | 固定数据快照与规则版本 | 确定性统计重跑一致；随机步骤记录种子与模型版本 |
| 可用性 | 若条件允许，5位非医疗背景成人完成模拟任务 | 记录完成率、错误、完成时间；不作为临床效果证据 |

上述数量和阈值是建议的项目验收目标，非赛事规定。人工编写或合成数据仅证明技术流程与规则行为；没有临床随访与确诊结局时，不报告早诊率、疾病预测准确率或治疗有效率。

后续真实研究需处理招募偏差、自报误差、失访、用药混杂与平台使用带来的行为改变。描述性关联不推导因果；“说明偏离候选比例”不能推广成大众药物滥用率。真实健康研究的知情同意、伦理与当地合规应在开展前落实。WHO强调健康AI应将伦理、人权与责任纳入设计和使用。[WHO健康AI治理](https://www.who.int/publications/i/item/9789240029200)

## 十 前端交付范围

用户端由每日健康、健康对话、病程、用药、历史线索及个人授权入口组成；每日健康显示有依据的简洁分析和建议，无当前不适时呈现康复、历史观察与季节环境关照；首次问询、补问、护理信息、用药记录、每日随访、提醒、授权与归档都在对话中完成。科研端包括研究总览、分析工作台、研究设计、队列与质量、记录溯源、数据底座、SciencePal运行和研究依据八个视图。详细布局、交互与独立前端结构见 `frontend-design.md`。

用户端与科研端采用两个独立HTML入口和独立业务脚本，共享绿色主题与基础图标。用户端不展示研究入口或角色切换；科研端提供只读观察、队列与分析。正式产品还需独立的研究权限与服务端隔离。

## 十二 演示与提交
